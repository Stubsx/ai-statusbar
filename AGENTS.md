# Repository Guidelines

## Project Structure & Module Organization

`Sources/LingmouCollectorCore/` is the canonical collector. It reads local Codex, Kimi Code, Kimi Work, Claude, Hermes, ZCode, and DSH (DeepSeek Harness web UI, via `~/.dsh` projection cache; per-session usage model comes from the session event-stream tail when a `zstd` binary is available) state and preserves the JSON contract consumed by all frontends. `Sources/LingmouCollectorCLI/` builds `lingmou-collector`, which emits JSON with `--json` and SwiftBar text by default; both modes share results across frontends through a 10s cache at `~/.ai-statusbar/collector-cache.json` (`--refresh` bypasses the read and rewrites it — the app uses file-triggered `--status-only` with a 5s fallback and `--metrics-only` every 30s so SwiftBar/Übersicht reuse fresh app state without blocking on quota or historical usage). `swiftbar-plugins/ai-cli-status.10s.sh` is the thin SwiftBar launcher. The native menu-bar app lives in `AIStatusBar/`: its Swift sources under `Sources/` are split by responsibility — `Models.swift` (JSON data models), `Stores.swift` (settings/status stores), `BusySessionTracker.swift` and `EventJournal.swift` (conservative tracking and local history), `Navigation.swift` (notification/task routing), `ExperiencePreferences.swift` (reminder preferences and quota deduplication), `Maintenance.swift` (login items and manual update check), `UIHelpers.swift` (icon spec, glass card modifiers, draggable hosting view), `HarnessConversations.swift` (shared per-harness conversation grouping for the panel and native menu), `StatusToolSection.swift`, `PanelPageTabs.swift` (four direct page buttons in a native horizontal scroll strip), `PanelView.swift`, `BallView.swift` (桌面卡片模式的收起态悬浮球：常驻状态球，点击展开面板，鼠标离开面板 10 秒自动收回), `SettingsView.swift`, `AppDelegate.swift`, and `main.swift` (entry point only). Edit these sources and `Info.plist`, then run `build.sh` to produce the local `灵眸.app` bundle (git-ignored build artifact, not tracked). Desktop-pet assets are data-driven: built-in pets live in `AIStatusBar/Resources/Pet/{pet-id}/` (state PNGs named `idle`/`working`/`loading`/`sleeping`/`celebrating`/`error` plus optional `-blink` and `working-type-left/right` variants, plus a `pet.json` manifest with `name` and optional `nsfw: true` flag that shows a badge in the picker); user-defined pets follow the same layout under `~/.ai-statusbar/Pets/` and are managed from the settings app's 桌宠 tab. Adding a built-in pet = drop a folder, no code changes. `uebersicht-widgets/ai-status.widget/index.jsx` provides the desktop widget and reads the collector from an installed `/Applications/灵眸.app`. App icons belong in `icons/`; release packaging is handled by `scripts/`. Generated DMGs under `dist/` are ignored.

The collector's `ActivityModels.swift`, `EventFeed.swift`, and `KimiWebNavigation.swift` are compiled into both SwiftPM and the native app; include them in standalone native checks. `KimiWebNavigation.swift` also carries the pure browser-tab reuse decision (focus the exact session tab, else navigate the frontmost same-origin tab, else new tab) that the native router executes via `osascript` in `Navigation.swift`, always falling back to a fresh tab on any failure; the toggle is `kimi_web_tab_reuse`. `ToolAdapter.swift` defines source-contributed adapter contracts. Pet package sharing lives in `PetSharing.swift` / `PetSharingViews.swift`; `Resources/PetGallery/index.json` is the bundled catalog. Product support boundaries and contributor guides live in `docs/`. `--events` / `--follow` read the opt-in local app event feed and do not collect data or run scripts.

The floating ball's ink and blue wash styles are drawn procedurally in `BallInkDrawing.swift` with fixed noise fields, cached in-memory textures and internal pigment layers. Keep the entire silhouette circular and stable with only a narrow antialiased edge; alpha must not vary with noise or animation phase. Keep all wash and pigment flow inside the circle, without outward bleed, dry gaps or a diffuse body halo. Neither uses image assets. The blue palette layers bright sky blue and diluted azure inside a clean rounded outline; preserve the approved ink palette separately. `BallInkFlow.swift` prepares 96 periodic frames per palette lazily in the background and plays them through a native `CALayer` (ink: 14-second idle / 8-second working loop; blue: 10-second idle / 6-second working loop, with stronger pigment travel for small-size visibility), preserving phase across speed changes and pausing while hidden or occluded. Switching appearance recreates the native view so pending frames cannot cross palettes. Resting freezes the base frame; Reduce Motion removes flow playback. The `lowEnergyMode` AppStorage switch in General settings removes both flow and orbit playback while preserving live gaze and blinking. Keep gaze/blink state inside the native view hosted by `BallTrackingFace` in `BallGazeTracking.swift`: update only two eye layers, without per-frame SwiftUI state/layout. Mouse-move/drag notifications wake tracking immediately; true pointer activity keeps the display clock awake for 0.5 seconds after movement, even when the gaze is already close to its target. Use the view display link on macOS 14+ and a coalesced Core Video display link on macOS 12/13, targeting at most 60fps; idle pointer polling remains a 4Hz fallback. Hidden views stop polling, display callbacks and mouse monitors. Mouse monitoring must not request keyboard events or new permissions, record a trajectory, or upload positions. Pointer movement does not disturb the wash. Include `BallGazeTracking.swift`, `BallInkDrawing.swift` and `BallInkFlow.swift` alongside `BallView.swift` in standalone native checks; `scripts/test-floating-ball.sh` checks the drawing, loop continuity and playback clock, and renders still/GIF previews. It also runs a real NSApplication event loop to verify changing presentation-layer frames in a transparent floating panel, hide/resume, palette switching, uninterrupted flow on hover, resting and Reduce Motion; still-image exports alone do not prove playback works.

## Build, Test, and Development Commands

```bash
./scripts/with-xcode.sh swift test
./scripts/with-xcode.sh swift run lingmou-collector --json
./scripts/check-open-source.sh
bash scripts/test-experience-visuals.sh
./AIStatusBar/build.sh
open "AIStatusBar/灵眸.app"
./scripts/build-dmg.sh
```

The first three commands validate collector output, tests, privacy checks, and Swift compilation. `build.sh` compiles universal `arm64`/`x86_64` app and collector binaries, embeds the collector, and signs both with the configured identity. Builds and public releases alike use the stable self-signed `Lingmou Local` identity (falling back to ad-hoc signing); Developer ID signing and Apple notarization are optional — set `SIGN_IDENTITY`/`NOTARY_PROFILE` before `release.sh`/`build-dmg.sh` to enable them. macOS TCC grants (screen recording, notifications) follow the signing certificate, so never mix identities across machines — unify via `scripts/import-signing-identity.sh` with a `.p12` exported from the primary build machine. `build-dmg.sh` rebuilds and creates a versioned installer in `dist/`.

After each completed work stage, run `./scripts/install-local.sh` to rebuild, replace `/Applications/灵眸.app`, and relaunch it, so the user always runs the latest build without being asked. It rebuilds first and never touches the running instance when the build fails.

## Coding Style & Naming Conventions

Use four-space indentation and Swift conventions (`PascalCase` types, `camelCase` properties and methods). Preserve encoded JSON field names because they are a shared API between the Swift core, native App, SwiftBar, and JSX. Keep collectors defensive: missing databases, malformed JSONL, or unavailable processes should degrade to empty/idle data instead of crashing. Do not edit files inside `灵眸.app` directly; rebuild them from source.

## Image Generation & Iteration Guidelines

- Treat images produced through Image 2, including images generated by the ImageGen skill, as Image 2 outputs. Prompts must explicitly suppress tiny fragmented details and request large, clean areas of flat color, controlled cel shading, coherent hair masses, and a readable silhouette. Always discourage mottled or speckled texture, noisy micro-detail, broken brushwork, excessive flyaway hair, patchy gradients, and other visually fragmented artifacts.
- Repeated image-to-image editing degrades quality. A chain such as A → B → C → D tends to accumulate clutter, mottling, inconsistent edges, and loss of the original clean rendering. Do not use a multi-generation edit chain by default.
- Use image-to-image only when the user explicitly asks to preserve the current character for a small adjustment, when the source image is intrinsically required, or when consistency must be very high—for example, deriving a blink or another action from an approved character frame.
- For ordinary design changes, improve the complete text-to-image prompt and regenerate a fresh image. When a reference is necessary, revise the prompt first and perform a single direct A → D reference-image generation instead of several incremental edits.
- During character exploration and before final approval, optimize for the prompt's repeatable overall effect rather than preserving the exact details of one sample. Hair, accessories, clothing details, and pose may change between drafts. The priority is a clean, reproducible design language without generation-induced degradation.
- After a master character image is approved, derive every consistency-sensitive action directly from that same master image in one hop. Never generate later actions from previously derived action frames. Prefer deterministic post-processing for background removal, alignment, cropping, or light texture cleanup instead of spending another image-to-image generation on those mechanical fixes.

## Testing Guidelines

Swift collector regression tests live in `tests/LingmouCollectorCoreTests/`. For collector changes, run `swift test` and JSON checks, then verify `busy`, `idle`, and `off` transitions against representative session events. For UI changes, rebuild, launch the app, and inspect menu-bar, popover, settings, and notifications. Include screenshots when visual behavior changes.

## Commit & Pull Request Guidelines

Recent commits use concise Chinese, action-oriented subjects such as `修复 Kimi 幽灵步骤误报` or `新增设置窗口`. Keep each commit focused and explain the behavioral reason. The `灵眸.app` bundle and `dist/` files are local build artifacts — never commit them. Pull requests should summarize the change, list validation commands, note affected agents/frontends, link relevant issues, and attach before/after screenshots for UI work.

Every release must include a committed `docs/releases/<tag>.md` describing concrete changes since the previous published version, based on the actual tag-to-tag diff. Do not copy the full product feature list or publish only GitHub-generated notes/a comparison link. Mention user-visible additions, improvements and fixes, plus relevant settings paths or migration requirements; end with the comparison link. `scripts/release.sh` requires these notes and publishes them with `--notes-file`. Read back the published release to verify its body and assets. When backfilling an old release, describe only that version's changes and preserve its tag and assets. Follow `docs/RELEASING.md` and `OPEN_SOURCE_CHECKLIST.md`.

## Security & Local Configuration

Never commit user session logs, databases, credentials, `~/.ai-statusbar/settings.json`, or personal absolute paths. Network quota behavior and privacy-sensitive permissions must remain clearly documented; permissions such as notifications and screen recording stay opt-in.
