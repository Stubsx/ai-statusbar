# 版本发布规范

每个正式 Release 都必须说明**相对上一个正式版本更新了什么**，不复制 README 的完整功能介绍，不把 GitHub 自动生成的比较链接当作更新说明。

## 更新说明

1. 核对上一正式版本的 tag 和本次发布提交，阅读两者之间的提交及实际代码差异。只写本版本确实包含的变化，避免把已发布功能或尚未合入的工作算进来。
2. 在 `docs/releases/vX.Y.Z.md` 保存中文说明并随代码提交。开头明确比较基准，例如“相较 v1.3.1，本次更新：”。
3. 至少写一条具体更新。按需要列出新增、优化、修复或兼容性变化；说明用户可感知的前后行为。新增开关应给出入口与作用，有迁移要求或实际限制时说明。没有变化的分类可以省略，不堆砌提交哈希或底层实现细节。
4. 末尾提供上一正式版本到本版本的完整比较链接。它用于追溯代码，不能代替正文。
5. 发布后回读 GitHub Release，确认正文与本地文件一致，标题、tag、安装包版本、DMG 和 SHA-256 附件均匹配。本地验证不能写成已在其他电脑或所有系统版本上验证。

示例：

```markdown
相较 v1.3.1，本次更新：

- 新增低能耗模式：可在「设置 → 通用」关闭浮球液体流动和光环旋转，保留眼睛跟随与状态提示。
- 修复……情况下……的问题。

[完整变更](https://github.com/Stubsx/ai-statusbar/compare/v1.3.1...v1.3.2)
```

## 发布流程

- 完成相关测试和 [公开发布检查清单](../OPEN_SOURCE_CHECKLIST.md)，将代码及版本说明提交并推送到 `main`，确认 CI 通过。
- 执行 `./scripts/release.sh vX.Y.Z`。脚本要求已提交的更新说明至少包含一条更新条目，再运行开源检查、构建 DMG、生成 SHA-256 文件、推送 annotated tag，并通过 `--notes-file` 写入正文。不得用 `--generate-notes` 代替人工整理的版本差异说明。
- 默认使用稳定的 `Lingmou Local` 自签名身份。Developer ID 和 Apple 公证是可选配置；启用时传入 `SIGN_IDENTITY` 和 `NOTARY_PROFILE`，按实际产物描述签名与公证状态。
- 发布后按上述要求回读验证，并运行 `./scripts/install-local.sh`，让本机安装版也使用刚发布的版本号。

## 补充历史说明

根据历史 tag 之间的真实差异补写对应的 `docs/releases/<tag>.md`，再执行：

```bash
gh release edit v1.3.1 --repo Stubsx/ai-statusbar --notes-file docs/releases/v1.3.1.md
```

补正文时保留原 tag、发布时间和安装附件，不把后续版本的修改补进旧版本。修改后回读正文确认已生效。
