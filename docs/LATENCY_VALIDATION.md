- 每 0.2 秒观察共享缓存和本地事件历史的文件变化，时间量化误差约 0.2 秒。没有在实发窗口强制刷新采集器。

## 已实施的修复

1. 状态与统计分离。文件变化触发本地状态采集，频繁变化合并为至多每秒一次；5 秒完整状态轮询兜底。Kimi Work、Hermes、ZCode 的数据库与 WAL 每 0.5 秒仅检查文件属性，覆盖文件长期保持打开、文件通知较晚的情况。用量／联网配额独立每 30 秒更新，手动刷新仍包含两者。
2. 保留完整共享 JSON。快速状态复用独立指标缓存，不把旧的统计结果当成新的任务快照覆盖。配额仍保留自身更新时间。SwiftBar／Übersicht 继续按原有频率读取共享缓存。
3. 减少重复工作。Codex 缓存未变化文件的解析信号，以修改时间、大小和 inode 失效；每次仍重新判断进程是否在线和状态是否过期。Claude 读取日志尾部，ZCode 优先读取结构化回合状态，Hermes 新版不再通过用量时间或全量网络连接猜忙碌。
4. 修复 Kimi CLI 的运行时改名：实际 `kimi-code` 与旧 `kimi` 都识别。Kimi Code／Work 读取主代理明确 end_turn，且有未闭合子代理或工具调用时不提前结束；新追问立即使上一轮结束信号失效。
5. 修复 Hermes 结束后仍亮忙碌约五分钟的问题。有效回合租约优先；没有租约时结合末条消息与明确结束原因，最近用量不再代表正在执行。错误原因记录为中断。旧 schema 保留兼容路径，其推断精度不等于新版。
6. ZCode 使用 running/completed/error/cancelled 回合状态，避免错误／取消被当成正常结束；刚结束即追问读取新的 user 消息，晚到的 assistant 元数据不会重开已结束任务。旧 schema 仍有保守回退。
7. Codex 从会话头核验 App／CLI 来源，防止索引回退或数据库版本不同造成归属混淆；修复带前导空格的进程 PID 解析，并识别 Python／Node 托管的 CLI。
8. 开启合并通知时，合并窗口由 4 秒缩为 1 秒；历史即时更新，等待回答仍即时处理。点击事件已读、定向清除系统通知对应记录、重启去重等已有行为保留。

## 效率与边界

最终采集器本机连续 5 次快速状态读取的墙钟耗时为 0.46—0.65 秒，中位数 0.47 秒。这是单轮扫描成本，活跃时会更频繁刷新；没有做长期电量／整机 CPU 对照，因此不据此宣称整机功耗降低。原始完整扫描曾出现约 1—2 秒的结果等待，另加 10 秒刷新间隔。

小于采样间隔的任务可能看不到中间忙碌，但具有明确结束记录的任务仍能补获结束事件。通知权限与用户偏好保持原样；没有把本地历史到达时间当成 macOS 通知横幅到达时间。未测试权限审批、工具调用、多代理长任务、断网与所有历史版本的真实交互，这些边界以回归 fixture 与支持矩阵为准。
